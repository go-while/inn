=encoding utf-8

=head1 NAME

controlbatch - Run controlchan against a batch file

=head1 SYNOPSIS

B<controlbatch> [I<feedsite> I<batchfile>]

=head1 DESCRIPTION

B<controlbatch> runs B<controlchan> against a batch file instead of a
channel feed.  It can be used to clear occasional backlogs building up
on a channel feed running B<controlchan>, or even to bypass the channel
feed altogether and process control messages as a file feed instead.

With no arguments, B<controlbatch> defaults to a I<feedsite> of
C<controlchan!> and a I<batchfile> of C<controlchan!> underneath
I<pathoutgoing> (as set in F<inn.conf>).  If you want to use different
values (for instance because you feed control messages to B<controlchan>
under another site name), both I<feedsite> and I<batchfile> must be
given together.

B<controlbatch> first makes sure that no other copy of itself is already
running, using a lock file named F<LOCK.controlbatch> in I<pathrun> (as
set in F<inn.conf>); if one is found, it silently exits.  It then finishes
the handoff of a previous run which was interrupted (see below), and merges
any leftover I<batchfile>C<.work> file (left behind by an interrupted
previous run, or by one which could not flush the site) into
I<batchfile>C<.doit>, after having flushed the site again so that B<innd>
no longer writes to it.  If I<batchfile> itself is not empty, it is renamed
to I<batchfile>C<.work>, and B<ctlinnd> is used to flush the site named
I<feedsite> so that B<innd> stops writing to it while it is being
processed; the flushed batch is then merged into I<batchfile>C<.doit> as
well.  Finally, if I<batchfile>C<.doit> is not empty, it is fed to
B<controlchan>, whose output is appended to F<controlbatch.log> in
I<pathlog> (as set in F<inn.conf>).

The merge of I<batchfile>C<.work> is done by staging and replacement, so that
no control article is lost, or processed twice, when the disk is full or when
B<controlbatch> is interrupted.  First, I<batchfile>C<.new> is written with
the content of I<batchfile>C<.doit> followed by that of I<batchfile>C<.work>.
Then I<batchfile>C<.work> is renamed to I<batchfile>C<.work.merged>, which
means that I<batchfile>C<.new> is complete.  Finally I<batchfile>C<.new> is
renamed to I<batchfile>C<.doit> and I<batchfile>C<.work.merged> is removed.
The next run completes the last steps if they were interrupted, looking at
the files which are there:  I<batchfile>C<.work.merged> together with
I<batchfile>C<.new> means that I<batchfile>C<.new> has to be published, and
I<batchfile>C<.work.merged> alone is removed only if I<batchfile>C<.doit> ends
with its content (otherwise B<controlbatch> stops with an error and keeps
all the files, so that you can check them).  Do not remove these files by
hand while B<controlbatch> may be running.

I<batchfile>C<.work> stays where it is until a flush of the site succeeds,
because B<innd> may still be writing to it; the batch file and
I<batchfile>C<.doit> are processed meanwhile.  If B<innd> is stopped for
good or the site has been removed from F<newsfeeds> (for instance during
a migration), the flush can never succeed.  Once you are sure that B<innd>
is not running, or no longer feeds this site, hand it over by hand with the
same staging and replacement, while no B<controlbatch> is running.  In
I<pathoutgoing>, first run B<controlbatch> once (its recovery of an
interrupted handoff runs even if the flush fails) and check that
I<batchfile>C<.new> and I<batchfile>C<.work.merged> are gone; if
I<batchfile> itself is not empty and there is no I<batchfile>C<.work>,
rename it to I<batchfile>C<.work>.  Then:

    cat batchfile.doit batchfile.work > batchfile.new &&
        mv batchfile.work batchfile.work.merged

(leave I<batchfile>C<.doit> out of the first command if it does not exist,
and use the real names of the files; the rename runs only if the copy
succeeded).  Run B<controlbatch> again: it
publishes I<batchfile>C<.new>, removes I<batchfile>C<.work.merged> and
processes the articles.  If the first command is interrupted, remove
I<batchfile>C<.new> and start again; if the second one is, B<controlbatch>
finishes the job.

I<batchfile>C<.doit> is removed only if B<controlchan> succeeds.  Otherwise,
it is kept so that it is processed again during the next run, and the number
of consecutive failures is recorded in I<batchfile>C<.tries>.  After three
consecutive failures (a value which can be changed by editing the I<maxtries>
variable at the beginning of the script), I<batchfile>C<.doit> is renamed to
I<batchfile>C<.failed.>I<date>, where I<date> is the current date in the
C<YYYYMMDDhhmmss> format, so that subsequent control articles can still be
processed.  A message is then written to F<controlbatch.log> and to standard
error (therefore usually mailed by B<cron>).  The control articles in that
file should be examined, and possibly processed again by hand, once the cause
of the failure has been fixed.  Note that the control articles processed
before the failure of B<controlchan> are processed again during the next
runs, and are also present in the set-aside file.

If you are running B<controlchan> as a channel feed, you may want to
call B<controlbatch> from B<cron> during a quiet period to clean up any
backlog:

    00 04 * * *     <pathbin>/controlbatch

Alternatively, if you would rather not run B<controlchan> as a channel
feed at all and instead process control messages in batches, use a
F<newsfeeds> entry like this one:

    controlchan!\
        :!*,control,control.*,!control.cancel\
        :Tf,Wnsm:

together with a B<cron> entry such as:

    30 * * * *     <pathbin>/controlbatch
