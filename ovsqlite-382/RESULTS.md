# ovsqlite write measurements for InterNetNews/inn#382: results

Generated by `mkresults.py` from the raw result files under `zfs/`; every table cell and every number in section 6 is computed there.
"source" is file:line of the run in `zfs/` (one JSON line per run).

## Setup

- FreeBSD 15.1-RELEASE in a VM; INN at main 4c5218607 with and without the prototype commit 47472af18.
- The overview is a ZFS dataset on a 5 GiB virtual disk that holds nothing else (history and logs are on the root filesystem), recreated for each run with recordsize as given and seeded with the same database: 300,000 articles in 200 groups, 57 MB, 4 KiB SQLite pages. Pool properties: `zfs/pool-properties.txt` (compression on, sync standard, txg timeout 5 s, one vdev).
- Articles are synthetic: one identical 40-line body, one newsgroup each (so one overview row per article; real traffic has crossposts), stored with the `trash` method, so only the overview writes.
- Articles are fed evenly spaced at a fixed rate (no bursts); after a warm-up one window is measured. No reader (nnrpd) was connected.
- In the 600-second jobs the three configurations ran in the order Today, `transtimelimit: 1`, Prototype; the 90-second rounds rotated the order.
- Configurations: **Today** = stock ovsqlite-server, commits 10 s after a transaction starts (`transtimelimit` default); **`transtimelimit: 1`**; **Prototype** = also commits once 250 ms pass without a further write (WAL mode only).

Columns:

- **server KiB/article**: bytes ovsqlite-server passed to `pwrite` (DTrace) per accepted article. This is SQLite's own output; see section 6 for how well it matched ZFS's logical write counter.
- **WAL frames/article**, **checkpoint pages**, **checkpoints**: solved exactly from the pwrite calls and bytes (frame = 24-byte header + page; checkpoint page = one page; WAL restart = 32-byte header) and from the fdatasync count (2 per checkpoint plus 1 per WAL restart).
- **WAL frames at end**: frames in the WAL when the window ended, not yet checkpointed (a checkpoint runs once the WAL holds 1000 frames and no transaction is open).
- **fdatasync**: calls by the server in the window. No `fsync` was called in any run; commits do not sync (`synchronous = NORMAL` in WAL mode).
- **disk**: bytes written to the pool's virtual disk (`iostat -I` in the guest), per second and per accepted article.

## Caveats

- One run per cell in section 1, and each recordsize ran in its own job at a different time, so differences of the size of the repeat runs cannot be told apart from job-to-job variation.
- The windows end at a fixed time, not at a checkpoint; see "over whole checkpoint cycles".
- Synthetic, evenly spaced articles with one group each that compress well; one 57 MB database; one VM with a virtual disk whose pool holds only the overview, so every transaction group's fixed cost is charged to it.
- Not covered: other filesystems, readers (nnrpd reading the WAL can delay checkpoints), expiry (which removes rows and rebalances the B-tree), crossposts, bursty arrival, rates between 0.04 and 0.5/s.
